## Findings

**1. HIGH, R-26 + C-2. Twenty native-dialog call sites are dead in half the runtimes.**
`window.confirm`, `window.prompt`, and `alert` appear 20 times across 6 files (admin, layout, search, settings, import, TodaClient). Windows WebView2 renders them, which is why the office never saw a problem. Under the WebKit webview (Linux/macOS builds, and any environment where the WebView2 dialog is suppressed) they return `undefined` instantly and silently:
- Sidebar route deletion: `confirm()` returns undefined → falsy → the delete never happens at all (safe but dead), while on the override path a missing `prompt()` result aborts with a required-reason alert that itself never shows.
- Admin Console, single-admin override (`handleSetActive`): the reason prompt returns undefined → the action can never be performed.
- Admin Console, reject a ticket: the note prompt short-circuits into the "No reason given." branch, then `confirm(undefined)` aborts the rejection.
Fix direction: one in-app dialog component (theme-token styled, Escape-closable, 44px buttons, focus trap) replacing all 20 call sites. This also fixes finding 7's root cause class.

**2. MEDIUM, C-2 + R-38. The Approvals tab shows two of the five ticket types without saying what is being approved.**
The payload description block renders only `route_delete`, `route_rename`, and `record_restore`. Tickets of type `user_deactivate` (filed by another Admin's deactivation under the two-key rule) and `db_restore` (filed when a clerk attempts a database restore) show only their label and the requester's reason. The approving Admin cannot see WHICH account would be deactivated or WHICH backup file would be restored before clicking Approve.
Fix direction: render the account name for `user_deactivate` and the backup filename/size for `db_restore` from `t.payload`, same pattern as the existing three types.

**3. MEDIUM, R-02. Em dashes in user-visible UI text (2 sites).**
- `src/app/settings/page.tsx:935` ("...could not be given a password from another computer — this...")
- `src/app/import/page.tsx:279` ("Admin only — a clerk signing in will be asked...")
A third occurrence is inside a code comment (`src/app/page.tsx:64`), not user-visible; fixed opportunistically with this item if approved.
Fix direction: colon, parentheses, or period per the rule.

**4. LOW, R-34 + R-25. Admin Console toasts and ticket status chips have no dark-mode variants.**
The success/error toasts (`bg-emerald-50 text-emerald-800`, `bg-red-50 text-red-800`) and the pending/approved/rejected chips (`bg-amber-50...`, `bg-emerald-50...`, `bg-red-50...`) carry hardcoded light tints with no `dark:` classes. In dark mode they render as bright pastel chips: readable (dark text on light chip, above 4.5:1) but off-system against the token-based chips used everywhere else (e.g. the Operational tab's action chips, which have proper dark variants).
Fix direction: add the `dark:` token variants, matching the existing action-chip pattern.

**5. LOW, R-03. Admin Console tab buttons and several small buttons sit under the 44px tap target.**
The four section tabs (`px-4 py-2`) and the Approvals/Administrative refresh buttons (`px-3 py-2` / `py-1.5`) compute to roughly 36px tall. Desktop-first app with mouse users, so the practical risk is low, but the rule sets 44px for buttons. Table row action buttons in the accounts table have the same height.
Fix direction: raise to `h-11` equivalents or `py-2.5`+ so hit areas clear 44px, matching the h-11 convention enforced in earlier passes.

**6. LOW, R-32. The Admin section tablist is not the complete ARIA tabs pattern.**
`role="tablist"` / `role="tab"` / `aria-selected` are present and each button is Tab-reachable and Enter-activatable, but there is no arrow-key navigation between tabs and no `aria-controls`/`tabpanel` linkage, so screen-reader users do not get the declared tab semantics.
Fix direction: add Left/Right arrow handling on the tablist and wire `aria-controls` + `role="tabpanel"` + `id`.

**7. LOW, R-27. Operational KPI cards use bare "..." text as the loading state.**
The three overview cards render `...` while `overview` is null. Loading exists (technically compliant) but every other data view in the app uses a spinner or skeleton, so this reads as broken rather than loading.
Fix direction: reuse the diagnostics card's spinner pattern.
